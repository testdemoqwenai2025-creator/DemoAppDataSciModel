AI / ML enablement on the dimensional layer

A Kimball dimensional warehouse is not just for dashboards. The conformed dimensions, fact tables and SCD2 history that power BI are exactly the assets that machine learning needs — governed features, point-in-time correctness, and consistent definitions between training and serving. This solution designs the dimensional layer with AI/ML enablement in mind from day one.

Four enablers of AI/ML on the warehouse

Each enabler turns a Kimball modelling asset into an ML platform capability.

Dimensional layer as the feature backbone

The conformed dimensions and fact tables are the canonical source for ML features. Instead of every data scientist rebuilding customer, product and time features from raw sources, the dimensional layer exposes them as governed, lineage-tracked, business-defined features. This shortens model development and improves feature consistency between BI and ML.

Feature store integration

The warehouse feeds an offline feature store that mirrors dimension and fact attributes keyed by the same surrogate keys used in BI. Online features for inference are served from a low-latency store populated from the same definitions. The result: training and serving features come from one definition, eliminating train/serve skew.

Point-in-time correctness

SCD Type 2 dimensions make point-in-time feature joins possible — a critical requirement for supervised ML. A model trained on “customer segment at time of purchase” can be assembled cleanly from the dimension history, without leakage from future state. This is a capability raw operational tables cannot provide.

Self-service analytics on the same model

Self-service analytics platforms and ML pipelines consume the same dimensional model through a shared semantic layer. Business analysts and data scientists see the same measures, the same hierarchies and the same definitions — disputes about “whose number is right” disappear because the source of truth is shared.

Analytics maturity model

The dimensional layer supports each stage of analytics maturity. Most organisations are at Stage 1 or 2; the goal of this solution is to make Stage 3 and 4 reachable without re-platforming.

1
Stage 1 — Descriptive

BI on the dimensional model. What happened, by dimension, over time.

Capability

2
Stage 2 — Diagnostic

Drill-across and drill-down analysis. Why did it happen, and where?

Capability

Bus matrix, drill-across, governed drill paths.

3
Stage 3 — Predictive

ML models trained on the dimensional layer. What will happen next?

Capability

Feature store, point-in-time joins, SCD2 history.

4
Stage 4 — Prescriptive

Model outputs fed back into operational systems. What should we do about it?

Capability

Online feature serving, governed model outputs, feedback loops into fact tables.

Designing for ML from day one

The cost of retrofitting a warehouse for ML is high — typically a full feature store rebuild plus a point-in-time correctness project plus a definition reconciliation exercise. Designing the dimensional layer with ML in mind from the outset avoids all three: conformed dimensions provide governed features, SCD2 history provides point-in-time correctness, and the business glossary provides the definition reconciliation.

Every model specification in this solution includes an “ML readiness” section that flags whether the fact and its dimensions are suitable for direct feature-store ingestion, and what additional enrichment (if any) is required.
