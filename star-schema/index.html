Star schema: the heart of the Kimball warehouse

A star schema places a single fact table at the centre, surrounded by denormalised dimension tables. It is the default shape for Kimball dimensional models because it is intuitive for business users, fast for BI tools, and easy to extend incrementally.

Reference star: Retail Sales
A canonical retail sales fact table surrounded by five conformed dimensions. Each dimension is joined to the fact on a surrogate key.

Fact table: fact_sales

Grain: one row per sales transaction line item. Measures are numeric and additive unless marked otherwise. Foreign keys reference the surrogate keys of the surrounding dimensions.

Best practices
  • Use surrogate keys for every dimension — never join on natural keys from source systems.
  • Keep fact tables narrow and long: many rows, fewer columns, all measures numeric.
  • Decouple attribute history from fact history using SCD Type 2 dimensions with effective date ranges.
  • Avoid null measures in fact tables — store zero for additive measures and a sentinel for unknowns.
  • Denormalise dimensions deliberately — a star, not a snowflake, unless there is a compelling storage or maintenance reason otherwise.
  • Document the grain in the fact table DDL comment so engineers never lose sight of what one row means.
Common pitfalls
  • Mixing grains in a single fact table (e.g. line-level and order-level measures in the same table).
  • Storing descriptive attributes in the fact table instead of the dimension.
  • Joining dimensions to facts on natural keys, which breaks when source systems reuse identifiers.
  • Forgetting to mark semi-additive measures, leading to incorrect “balance as of” totals across time.
  • Over-snowflaking dimensions into deeply normalised chains that hurt query performance and readability.
Star vs snowflake

A star schema denormalises each dimension into a single wide table. A snowflake schema normalises dimensions further, splitting attributes into additional tables (for example a category table separate from the product table). Kimball strongly prefers stars for their query simplicity and performance with modern columnar engines.

Snowflaking is appropriate only when there is a clear storage or maintenance benefit — for example, when a dimension attribute set is extremely large and rarely queried, or when a sub-attribute is shared across many parent rows and maintained independently. The default answer in this solution is a star; departures from that default are documented in the model specification.
