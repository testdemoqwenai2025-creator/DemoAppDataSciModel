Data version control (DVC)

DVC (Data Version Control) brings git-like versioning to data. Each fact table load gets a DVC commit; rolling back the warehouse becomes a git checkout. This closes the gap between code versioning and data versioning — the missing piece for reproducible scientific platforms.

See dvc diff, dvc dag, and rollback with sample output.
The problem DVC solves

Git versions code. But data — fact tables, dimension exports, model artifacts — is too large for git. The result: code and data drift apart. You check out an old commit, but the data it was built against is gone. Reproducibility breaks.

DVC fixes this. It tracks data hashes in git (via small .dvc metafiles) and stores the actual data in a separate cache (S3, GCS, local). A git checkout + dvc checkout restores both code and data to a consistent state. Data changes become diffable, reviewable, and auditable — just like code changes.

DVC is installed in this sandbox (pip install dvc). Run dvc --version to verify.

The 10 commands you need to version data alongside code.

DSModelPro pipeline (dvc.yaml)

Define the warehouse build as a DVC pipeline. Each stage depends on the previous; DVC only re-runs stages whose inputs changed.

dvc.yaml
# dvc.yaml — DSModelPro data pipeline
# Defines stages for the dimensional warehouse build

stages:
  ingest_raw:
    cmd: python scripts/ingest.py --source bids --output data/raw/
    deps:
      - scripts/ingest.py
    outs:
      - data/raw/
  
  build_dim_workflow_run:
    cmd: python scripts/build_dimension.py --dim workflow_run
    deps:
      - data/raw/
      - scripts/build_dimension.py
    outs:
      - data/dim_workflow_run.csv
  
  build_fact_neuroimaging:
    cmd: python scripts/build_fact.py --fact neuroimaging_scan
    deps:
      - data/raw/
      - data/dim_workflow_run.csv
      - scripts/build_fact.py
    outs:
      - data/fact_neuroimaging_scan.csv
  
  compute_qc:
    cmd: python scripts/compute_motion_qc.py
    deps:
      - data/fact_neuroimaging_scan.csv
    metrics:
      - metrics/qc_scores.json:
          cache: false

The versioning workflow

Five steps to make data changes as reviewable as code changes.

1
Track data with DVC

Run dvc add on each fact table and dimension CSV. DVC creates .dvc metafiles that git tracks. The actual data goes to DVC cache (local or remote).

2
Commit metafiles to git

git add data/fact_neuroimaging_scan.csv.dvc && git commit. The metafile records the data hash — git now knows which version of the data belongs to this commit.

3
Push data to remote storage

dvc push uploads data to S3/GCS/Azure. Code goes to git; data goes to DVC remote. Both are versioned together.

4
Roll back to a previous version

git checkout <old-commit> && dvc checkout. The code reverts AND the data reverts to match. No more "which version of the data produced this result?"

5
Diff data between versions

dvc diff HEAD~1 HEAD shows which rows changed, were added, or were deleted. Data changes become reviewable like code changes.

How DVC fits the DSModelPro architecture

Data products as DVC-tracked artefacts. Every fact table and dimension export in the data mesh becomes a DVC-tracked file. When a domain team publishes a new version of their data product, they run dvc add + git commit. Consumers can pin to a specific version — no surprises when the data changes.

Reproducibility closes the loop. Combined with dim_workflow_run (provenance), DVC gives you two layers of reproducibility: the warehouse row tells you which pipeline produced a result; DVC tells you which version of the data the pipeline consumed. Together, they make every result fully traceable.

Pipeline as code. The dvc.yaml file is versioned in git alongside the modelling code. Changing the pipeline is a code change — reviewed, tested, merged. No more "who changed the ETL and when?"
