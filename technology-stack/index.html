Technology stack — what DSModelPro actually uses

An honest accounting of the libraries and platforms behind DSModelPro. The web application stack is real and integrated. The scientific computing stack is documented as the target architecture — most of it is not yet wired in, because DSModelPro is currently a reference and documentation platform, not a processing pipeline. Each scientific library below is marked with its integration status.

What DSModelPro is — and what it is not

DSModelPro is a dimensional data warehouse reference platform. It models how scientific data — climate, genomics, astrophysics, neuroimaging — should be structured in a Kimball warehouse, governed, and made queryable. The web stack below is real and runs the application you are using right now.

DSModelPro is not a processing pipeline. It does not run fMRIPrep, GATK or FSL. It does not process NIfTI files or call variants. The scientific libraries listed below are the target ecosystem — what a production deployment would integrate. The current app describes how those outputs land in the warehouse, not how they are produced.

This is deliberate. The dimensional model is the hard part to get right; the processing tools are well-established. DSModelPro solves the modelling problem first. Integrating real processing is the next evolution phase.

Advanced evolution thoughts
Where DSModelPro could go next — from reference platform to production scientific data platform.

Phase 1: Real neuroimaging processing

Add a Python mini-service (FastAPI + nibabel + pybids) that accepts a BIDS dataset URL, runs bids-validator, and returns a dataset manifest. The Live Demo could then show real BIDS datasets (e.g. OpenNeuro) instead of synthetic data. This is the lowest-friction integration — nibabel and pybids are pure Python, no GPU needed.

Phase 2: In-browser brain image viewing

Integrate Niivue — a WebGL NIfTI viewer that renders brain images in the browser. Upload a .nii.gz file, see it rendered as a slice/orthogonal view, and the metadata (TR, TE, voxel size) auto-populates the fact table spec. This would make the neuroimaging page genuinely interactive rather than descriptive.

Phase 3: Real processing via Docker

Wrap fMRIPrep, GATK and CESM2 in Docker containers orchestrated by a mini-service. The Live Demo could submit a real (small) BIDS dataset to fMRIPrep and watch the workflow_run row appear in dim_workflow_run as it completes. Requires a server with Docker — not possible in this sandbox, but the architecture supports it.

Phase 4: Jupyter notebooks in-app

Embed JupyterLite (Jupyter compiled to WebAssembly) so users can write Python notebooks that query the dimensional model — all client-side, no server. Combined with the DataUploadPanel, this turns DSModelPro into a self-contained analytical workbench.

Phase 5: Version-controlled data products

Integrate DVC (Data Version Control) so data products are versioned alongside the code. Each fact table load gets a DVC commit; rolling back to a previous version of the warehouse becomes a git checkout. This closes the gap between code versioning and data versioning.

Phase 6: Real-time collaboration

Add WebSocket-based multi-user editing so teams can collaboratively annotate the bus matrix, dimension attributes and data quality rules. The event-stream-service already demonstrates the WebSocket plumbing — extending it to collaborative state is a natural next step.

GDPR & Data Protection Notice

This demonstration application is designed to operate without collecting personal data from visitors. No cookies are set for analytics or tracking purposes, and no personal information is transmitted to third parties. Theme preferences are stored locally in your browser only.

In line with the UK GDPR and the EU General Data Protection Regulation (Regulation (EU) 2016/679), any production deployment of the underlying dimensional model must implement appropriate technical and organisational measures, including data minimisation, purpose limitation, storage limitation, access controls, and lawful basis documentation for any personal data processed within the warehouse. Data subject rights — including access, rectification, erasure, restriction, portability and objection — must be supported by the surrounding governance framework and reflected in the conformed dimension designs.

For data protection enquiries relating to this artefact, contact the repository owner via the email above. This notice is provided for demonstration purposes and should be reviewed by your Data Protection Officer before any production use.
