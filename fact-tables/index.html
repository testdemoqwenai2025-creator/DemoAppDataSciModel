Fact table patterns

Fact tables capture business events at a declared grain. Kimball defines three primary patterns — transaction, periodic snapshot and accumulating snapshot — plus the factless fact for coverage and event tracking. Choosing the right pattern is the single most important fact-table design decision.

The four patterns

Each pattern optimises for a different analytical question. A mature warehouse will contain examples of all four.

Transaction fact
Grain

One row per business event at a point in time

When to use

Use when the event itself is the unit of analysis — a sale, a click, a shipment, a claim.

Example

fact_sales — one row per sales transaction line item, timestamped to the second.

Measures

Mostly additive measures (quantity, amount). High row volume, low latency expectation.

Periodic snapshot fact
Grain

One row per entity per time period (e.g. daily, weekly, month-end)

When to use

Use when you need to report balances or status at regular intervals — inventory, account balances, headcount.

Example

fact_inventory_daily — one row per product per store per day, capturing on-hand quantity and valuation.

Measures

Semi-additive measures — additive across product and store, but not across time (you do not sum “balance as of yesterday” and “balance as of today”).

Accumulating snapshot fact
Grain

One row per entity lifecycle, updated as milestones occur

When to use

Use for pipeline-style processes with well-defined milestones — order fulfilment, claims processing, loan origination.

Example

fact_order_fulfilment — one row per order, updated at each milestone: placed, picked, packed, shipped, delivered, returned.

Measures

Milestone dates and durations, plus cumulative measures (total quantity shipped, total refunded). The same row is revisited many times.

Factless fact table
Grain

One row per event that has no measures — only context

When to use

Use to track coverage (which students were eligible for which classes on which days) or events that are themselves the measure (a click, a contact, a visit).

Example

fact_student_attendance — one row per student per class per day, no measures. Counting rows gives attendance; counting distinct keys gives coverage.

Measures

None by definition — analysis is done by counting rows or distinct dimension combinations.

Measure additivity

Additivity determines how a measure can be aggregated. Documenting it on every measure prevents the most common reporting error: summing a measure that should not be summed.

Additive
measure class

Can be summed across all dimensions — including time. The most flexible measure type. Example: sales quantity, sales amount.

Semi-additive
measure class

Can be summed across every dimension except time. Snapshot balances (inventory, account balance, headcount) are the classic case. Must be averaged, last-value, or first-value across time.

Non-additive
measure class

Cannot be summed across any dimension. Ratios, percentages, averages, and distinct counts belong here. Store the underlying numerator and denominator as additive measures and recompute the ratio in the BI layer.

Pattern: Entity-opportunity matching (recommendation systems)

A fourth pattern that recurs across talent marketplaces, clinical-trial recruitment, mentor matching, and product recommendations. The core challenge is not the match itself — it's modelling the feedback loop between a match and its outcome, so the matching algorithm can be measured and improved.

The four-table pattern
Two dimensions (entity, opportunity) + two facts (match, outcome). The outcome fact is SCD2 — it captures whether the match led to thriving, measured over time.
DIMdim_entity

One row per entity being matched — person, patient, buyer, rider. Includes consent tier and protected attributes (for bias detection).

DIMdim_opportunity

One row per opportunity — role, trial, product, project. Includes requirements (skills, eligibility, price).

FACTfact_match

Grain: entity × opportunity × time. Captures match_score, matched_by (algorithm/human/agent), match_method. Transaction fact — one row per match event.

FACTfact_outcome

Grain: entity × opportunity × time. Captures thriving_score, retention, performance. Periodic snapshot — updated monthly, SCD2 tracks trajectory.

Worked examples
Talent matching

entity = person, opportunity = role. Outcome = 90-day thriving score. Skills graph as a conformed dimension.

Clinical-trial recruitment

entity = patient, opportunity = trial. Outcome = enrolment success + 6-month efficacy. Eligibility criteria as a dimension.

Marketplace

entity = buyer, opportunity = product. Outcome = purchase + 30-day retention. Recommendation algorithm as matched_by.

-- Matching-system star schema (applies to talent, trials, marketplace)
CREATE TABLE dim_entity (
  entity_key        BIGINT PRIMARY KEY,
  entity_id         VARCHAR(50) NOT NULL,      -- person_id, patient_id, buyer_id
  entity_type       VARCHAR(20),               -- PERSON, PATIENT, BUYER
  -- Consent + governance (GDPR for personal data)
  consent_tier      SMALLINT,                  -- 0=anonymous, 1=aggregated, 2=identified
  protected_attrs   JSONB,                     -- gender, ethnicity, age_band (for bias checks)
  UNIQUE (entity_id)
);

CREATE TABLE dim_opportunity (
  opp_key           BIGINT PRIMARY KEY,
  opp_id            VARCHAR(50) NOT NULL,      -- role_id, trial_id, product_id
  opp_type          VARCHAR(20),               -- ROLE, TRIAL, PRODUCT
  requirements      JSONB,                     -- skills needed, eligibility, price
  UNIQUE (opp_id)
);

-- Transaction fact: one row per match event
CREATE TABLE fact_match (
  match_key         BIGINT PRIMARY KEY,
  entity_key        BIGINT NOT NULL REFERENCES dim_entity,
  opp_key           BIGINT NOT NULL REFERENCES dim_opportunity,
  match_score       DECIMAL(5,4),              -- 0.0000 to 1.0000
  matched_by        VARCHAR(20),               -- ALGORITHM, HUMAN, AGENT
  match_method      VARCHAR(50),               -- e.g. 'cosine_similarity', 'manual', 'agent_v2'
  matched_at        TIMESTAMP NOT NULL
);

-- Periodic snapshot: thriving/outcome over time (SCD2 trajectory)
CREATE TABLE fact_outcome (
  outcome_key       BIGINT PRIMARY KEY,
  entity_key        BIGINT NOT NULL REFERENCES dim_entity,
  opp_key           BIGINT NOT NULL REFERENCES dim_opportunity,
  snapshot_date     DATE NOT NULL,
  thriving_score    DECIMAL(4,3),              -- 0.000 to 1.000 (composite)
  retained          BOOLEAN,                   -- still in the match?
  performance_score DECIMAL(4,3),
  UNIQUE (entity_key, opp_key, snapshot_date)
);

Why the outcome fact is the hard part

Anyone can build a match score. The hard problem is measuring whether the match worked. Thriving is a composite, slowly-changing metric — engagement + performance + retention + self-report — and it's subject to survivorship bias (you only see outcomes for people who accepted the match). The outcome fact must support counterfactual queries (matched vs unmatched cohorts) for the matching algorithm to be improvable. That's data science, not BI.

Advanced: Agent-queryable data layer

The next frontier. Current BI serves humans — dashboards, charts, drag-and-drop. Current AI chatbots translate human questions into SQL. Neither treats AI agents as first-class consumers of the data layer. DSModelPro's pattern: a semantic API that agents query directly, with enforced grain, conformance, consent, and audit — so agents get governed, structured answers, not free-form SQL they might get wrong.

The problem with agents writing SQL

When an AI agent writes its own SQL against a warehouse, three things go wrong: (1) it picks the wrong grain — summing a semi-additive balance across time, or joining a snapshot fact to a transaction fact; (2) it ignores consent — querying protected attributes the human user isn't authorised to see; (3) it's unauditable — there's no record of what the agent asked, why, or whether the answer was biased.

The fix is not “better prompt engineering.” The fix is a machine-readable data contract that sits between the agent and the warehouse. The agent declares what it wants (an entity, an opportunity, a metric, a time window). The contract validates the request against grain rules, enforces consent, runs bias checks, logs the query, and returns a structured answer. The agent never touches SQL.

The architecture — five layers
From agent request to governed answer. Each layer enforces one constraint.
1. Agent

Declares intent: "Recommend 3 opportunities for person X, with evidence."

2. Data Contract

Validates the request: grain, consent, allowed metrics. Rejects invalid queries.

3. Semantic API

Translates intent → governed query plan. No raw SQL — structured metric definitions.

4. Bias Hooks

Runs parity checks, disparate-impact ratios. Blocks biased results before return.

5. Audit Log

Logs to fact_agent_query: who asked, what, when, what was returned. Full traceability.

Agent Data Contract — machine-readable schema
The contract declares what agents can query, at what grain, with what consent. Agents read the contract before querying — they never guess.
# agent_data_contract.yaml
# Machine-readable contract that AI agents consume before querying the warehouse.
# The agent reads this, validates its request against it, then calls the semantic API.

contract_version: "1.0"
warehouse: "talent_analytics"

# What entities can agents query about?
entities:
  - name: person
    grain: "one row per individual"
    consent_required: true
    consent_tiers: [1, 2]          # agents need at least tier 1 (aggregated)
    protected_attrs: [gender, ethnicity, age_band]
    # Agents CANNOT query protected_attrs directly — only via bias-check endpoints
    queryable_attrs: [skills, interests, assessment_scores, match_history]

# What opportunities can agents match against?
opportunities:
  - name: role
    grain: "one row per open role"
    queryable_attrs: [team, requirements, location, seniority]

# What metrics can agents compute?
metrics:
  - name: match_score
    type: additive
    grain: "entity × opportunity × time"
    description: "Cosine similarity between entity skills and opportunity requirements"
    valid_time_windows: [7d, 30d, 90d]

  - name: thriving_score
    type: semi_additive
    grain: "entity × opportunity × snapshot_date"
    description: "Composite: engagement 0.3 + performance 0.4 + retention 0.3"
    # Agents MUST specify a single snapshot_date — cannot average across time
    constraint: "require_snapshot_date = true"

  - name: match_quality
    type: non_additive
    grain: "cohort × time_window"
    description: "Thriving score for matched cohort minus thriving score for unmatched cohort"
    # COUNTERFACTUAL — agents must declare both cohorts
    constraint: "require_counterfactual = true"

# What can agents NOT do?
prohibited:
  - "sum thriving_score across time (semi-additive violation)"
  - "query protected_attrs without bias-check endpoint"
  - "join fact_match to fact_outcome without declaring the time lag"
  - "return individual-level results when consent_tier < 2"

# Bias checks that run automatically
bias_checks:
  - type: statistical_parity
    description: "Match score distribution must not differ by >10% across protected attrs"
    action_on_fail: block_and_flag

  - type: disparate_impact
    description: "80% rule — selection rate for any protected group must be >= 80% of highest"
    action_on_fail: block_and_flag

# Audit logging
audit:
  log_to: fact_agent_query
  fields: [agent_id, query_intent, query_plan, result_summary, bias_check_result, timestamp]
  retention: "7 years"
fact_agent_query — auditing agent behaviour
Every agent query is logged. You can audit what agents asked, what they got back, and whether bias checks fired. This is the table regulators will ask for.
CREATE TABLE fact_agent_query (
  query_key            BIGINT PRIMARY KEY,
  agent_id             VARCHAR(100) NOT NULL,   -- e.g. 'talent-matcher-v2'
  agent_version        VARCHAR(20),              -- for reproducibility
  query_intent         TEXT NOT NULL,            -- natural-language intent
  query_plan           JSONB NOT NULL,           -- structured plan (entity, opp, metric, window)
  result_summary       JSONB,                    -- what was returned (summary, not raw rows)
  entities_returned    INTEGER,                  -- count
  consent_tier_used    SMALLINT,                 -- what consent level was applied
  bias_check_result    JSONB,                    -- parity, disparate_impact outcomes
  bias_check_blocked   BOOLEAN,                  -- was the result blocked?
  query_duration_ms    INTEGER,
  queried_at           TIMESTAMP NOT NULL,
  -- Provenance
  user_id              VARCHAR(50),              -- who triggered the agent
  session_id           VARCHAR(100)
);

Counterfactual endpoints — the novel capability
Agents can ask “what if?” questions against governed counterfactual logic. This is what makes the layer data science, not BI.

A human dashboard shows what happened. An agent needs to know what would happen under different assumptions. The semantic API exposes three counterfactual endpoints that agents can call:

/counterfactual/match

“If person X had skill Y, what opportunities would they match?” — injects a hypothetical skill and re-runs the match score.

/counterfactual/cohort

“Did the matched cohort thrive more than the unmatched cohort?” — propensity-scored counterfactual with confidence interval.

/counterfactual/bias

“Would the top-3 recommendations change if protected attrs were removed?” — fairness audit on the model itself.

Each endpoint returns a structured JSON answer with confidence intervals, the query plan that produced it, and a bias-check result. The agent can cite the evidence — “I recommend these 3 opportunities because the counterfactual cohort analysis shows a 23% thriving uplift (95% CI: 14-31%)” — rather than asserting a recommendation without justification.

Why this is novel — and why clients will care

Eightfold, Gloat, and Workday all build dashboards for humans. Nobody has yet shipped a talent data layer that AI agents query directly — where an agent asks “which 3 opportunities should I surface to person X, and what's the evidence they'll thrive?” and gets a governed, auditable, bias-checked answer back.

This matters because agents are becoming the primary consumers of analytical work. Within 2-3 years, most “BI queries” will be agent-initiated, not human-initiated. The platforms that win will be the ones with a governed agent-query layer — not the ones with the prettiest dashboard. DSModelPro's agent-queryable pattern is the architectural answer to that shift.

Commercial positioning: when a client asks “can your platform support AI agents?”, the answer is not “yes, we have a chatbot that writes SQL.” The answer is “yes, we have a machine-readable data contract, a semantic API, bias hooks, and an agent-query audit fact table — agents query the contract, not the warehouse.” That's a materially different and stronger answer.

Challenging datasets — the diagnostic

When a client hands you a 50-column CSV with no data dictionary, you don't face one pattern in isolation — you face the diagnostic: which pattern applies, which grain is correct, which columns are dimensions vs facts. These seven demos teach the thinking of a senior data engineer, not just the patterns.

1. The Grain Detective

10 rows of mixed-grain data. Click “Detect grain” to see how to split one dataset into two fact tables before it double-counts your BI.

2. Pattern Diagnostic Wizard

Answer 4 questions about your dataset. Get a recommended fact-table pattern + schema. The meta-skill: how to figure out which pattern you need.

3. Late-Arriving Facts

A fact arrives 3 days late. The dimension changed. See the wrong join (current segment) vs the correct as-of join (SCD2 segment at business date).

4. Column Classifier

10 columns, no data dictionary. Assign each to dimension / additive / non-additive / audit / junk. Reveals the key lesson: ratios are non-additive, audit columns don't belong in the model.

5. Bridge Table — many-to-many with role

Students in classes, with TAs. Naive model double-counts. Bridge table with a role attribute fixes it. The Kimball answer to “what if the relationship itself has attributes?”

6. Role-Playing Dimensions

order_date, ship_date, estimated_delivery, actual_delivery — all reference dim_date. See the naive (four WHERE clauses) vs correct (four aliased joins) approach.

7. Ragged Hierarchy

Org chart with variable depth (3–5 levels). Fixed-depth breaks. The path-enumeration bridge handles any depth with a single join — no schema change when a 6th level appears.

The single grain rule

A fact table has exactly one grain. If you find yourself wanting to add a measure that does not make sense at the declared grain, do not bolt it on — that measure belongs in a different fact table. Mixing grains is the most common cause of incorrect aggregates and unexplained BI totals.

When two related grains are needed (for example, line-level sales and order-level sales), model them as two separate fact tables that share conformed dimensions. The drill-across capability of the conformed dimensions lets BI tools combine them at query time without violating either grain.
