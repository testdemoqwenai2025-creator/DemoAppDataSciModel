Streaming analytics: real-time fact tables

Traditional dimensional warehouses load nightly. Modern platforms cannot wait — a transient astronomical alert must reach the warehouse in 30 seconds, not 30 hours. Streaming analytics closes the gap by maintaining real-time materialised views of fact tables, with the columnar warehouse serving as the cold-history layer underneath.

The fact table is a materialised view, not a load target

In a streaming warehouse, the fact table is no longer something ETL writes to. It is a materialised view of the event stream, maintained continuously by a stream processor. The same view can be rebuilt from scratch by replaying the stream — there is no separate "batch" truth.

The practical consequence is that freshness becomes a property of the view, not of a schedule. A dashboard that needs 30-second freshness reads from the hot view; a statistical analysis that needs three years of history reads from the cold view. Both are projections of the same event log; both are consistent with each other within their respective freshness windows.

Hot / cold streaming architecture
Flink consumes the event stream and maintains three projections: a hot key-value store for the last 7 days, the columnar warehouse for cold history, and the online feature store for ML inference. The query federation layer merges hot and cold transparently.

Lambda, Kappa, and the hybrid

Three architectural patterns for combining batch and streaming. This platform uses the hybrid because pure Kappa is too expensive at scientific scale and pure Lambda is too brittle.

Lambda
Batch + speed layers, served by a merged view
Batch

Nightly full reload from the event log into the warehouse (the slow path). Authoritative, comprehensive, eventually consistent.

Speed

Stream processor (Flink / Kafka Streams) maintains a real-time delta (the fast path). Approximate, partial, low-latency.

Serving

Query layer merges the batch view with the speed delta. Conflicts resolved by preferring the speed layer for recent timestamps.

Tradeoff

Two code paths to maintain. The speed layer is often a poor cousin to the batch layer — different logic, different bugs.

Kappa
One engine, one path: stream-only
Batch

There is no separate batch layer. The "batch" view is a replay of the stream from the beginning, materialised by the same engine.

Speed

The same stream processor handles both live and historical. A "rebuild" is just a seek to offset 0 and a re-run.

Serving

Single query layer over a single materialised view. No merge logic, no conflict resolution.

Tradeoff

Replays are expensive for very long histories. Imposes discipline: every transformation must be a pure function of the event log.

Hybrid (this platform)
Kappa for hot facts, batch for cold history
Batch

Cold history (older than 7 days) lives in the columnar warehouse, loaded by the nightly batch. Optimised for ad-hoc analytics.

Speed

Hot facts (last 7 days) live in a streaming materialised view (Flink). Optimised for low-latency dashboards and alerting.

Serving

Query federation transparently merges hot and cold. The user does not know which layer answered.

Tradeoff

Requires the federation layer to understand timestamp boundaries. Worth it: cold queries are fast and cheap; hot queries are fresh.

Windowing matters

Streaming aggregates depend on windowing. Tumbling windows (1-minute, 5-minute, hourly) are simple but rigid. Sliding windows smooth over boundaries. Session windows group by activity gaps — essential for user-behaviour analytics.

The platform standardises on tumbling windows aligned to the conformed date dimension. A 5-minute aggregate window starts at :00, :05, :10 — never at :03. This means every streaming aggregate rolls up cleanly into the dim_date hierarchies, with no awkward boundary alignment.

Exactly-once is a lie (and that’s fine)

Stream processors advertise "exactly-once" semantics. What they actually deliver is "at-least-once with idempotent sinks" — which is exactly-once in effect, but only if the sink is idempotent.

The fact-builder service makes the warehouse idempotent by using INSERT … ON CONFLICT (event_id) DO NOTHING. Duplicate events are silently dropped. The trade-off: the warehouse cannot tell you how many duplicates the stream produced — but it does not need to, because the duplicates do not affect the answer.
