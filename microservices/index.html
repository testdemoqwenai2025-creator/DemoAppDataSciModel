Distributed Platform

Microservices architecture, guided by the bus matrix

The same enterprise bus matrix that frames the dimensional model doubles as a service decomposition guide. Each row becomes a service that owns a business process; each conformed dimension becomes a master-data service. The warehouse is no longer a monolith — it is a read-side projection of the event streams emitted by autonomous services.

The deeper insight

A common microservices failure mode is decomposing services around technical layers (a “REST service”, a “persistence service”, a “notification service”). That decomposition optimises for reuse and destroys cohesion. Decomposing around the bus matrix instead gives every service a single business-process reason to exist, a single team to own it, and a contract (the conformed dimensions it consumes) that is stable across reorganisations.

Equally: the warehouse is not a service. It is a materialised view of the event streams. Treat it as a read-side projection in a CQRS sense, and the temptation to put business logic in ETL disappears — the logic lives in the service that owns the business process, and the warehouse simply projects.

Service decomposition rules

Four rules keep the decomposition honest. Each rule traces back to the bus matrix.

One service per bus matrix row

Each row of the enterprise bus matrix is a business process. A service that owns one business process has a single reason to change, a single team that owns it, and a clear contract with the conformed dimensions it consumes.

One service per conformed dimension

A conformed dimension is mastered once and consumed many times. The service that masters it owns the surrogate key assignment, the SCD2 history and the glossary definition. Other services consume it via a stable read API.

Database-per-service, no shared writes

Each service owns its own persistent store. No service writes to another service’s tables. Cross-service reads happen via published APIs or via the warehouse, never via direct database access. This is what makes the services independently deployable.

Async by default, sync only when needed

Service-to-service calls default to event publication on a shared broker. Synchronous calls are reserved for read-heavy serving paths where latency matters (e.g. query federation). Async defaults preserve service autonomy and let the warehouse consume the same events as everything else.

Distributed patterns in use

Four patterns cover the bulk of cross-service concerns in this platform.

Saga
Problem

A business transaction spans multiple services (e.g. register a sample → assign a workflow run → emit a fact).

Solution

A sequence of local transactions, each emitting an event that triggers the next. Compensating actions roll back on failure. No distributed two-phase commit.

Outbox
Problem

A service must update its own database AND publish an event — atomically. The classic "dual write" problem.

Solution

Write the event to an outbox table in the same database transaction as the business change. A separate process polls the outbox and publishes to Kafka. At-least-once delivery, with consumers idempotent on event ID.

CQRS
Problem

The write model (event-sourced, normalised) is a poor fit for the read model (denormalised, query-optimised).

Solution

Separate the write side (commands → events → state) from the read side (projections → materialised views). The dimensional warehouse is itself a read-side projection of the event streams.

API Gateway / BFF
Problem

Many consumers (BI tools, ML notebooks, partner systems) need to query the platform; each has different needs.

Solution

A thin API gateway handles auth, rate limiting and routing. Backend-for-Frontend services tailor responses per consumer. The query-federation service is the BFF for analytical workloads.

Service mesh

A service mesh (Istio / Linkerd) handles cross-cutting concerns — mTLS between services, retries, timeouts, circuit breaking and traffic shifting for canary releases. Each service in this platform runs in its own Kubernetes namespace with a sidecar proxy; application code is unaware of the mesh.

The mesh is also where distributed tracing headers are injected. Every request entering the API gateway gets a trace ID; that ID flows through every service hop and into the event metadata, so a slow query in the warehouse can be traced back to the instrument read that started it.

Governance as a service

The governance-service is the single source of policy. Glossary terms, quality rules and access policies live there; other services query it at startup and subscribe to a policy.changed topic for hot updates. No service hard-codes a data classification or a retention rule.

This is what makes federated governance possible: each domain team owns its services, but governance is centrally defined and locally enforced. The bus matrix is the map; the governance service is the rulebook.

Why this matters for scientific computing

Scientific platforms fail in a specific way: a brilliant research team builds a one-off pipeline, the pipeline becomes load-bearing, the original team moves on, and the next team cannot reproduce a single result. Microservices decomposed around the bus matrix — with provenance as a first-class service — break that cycle. Every workflow run is a row in dim_workflow_run. Every container image, every input dataset, every parameter set is captured. Reproducibility becomes a query, not an archaeological dig.
