Autonomous vehicles: sensor fusion, long-tail, handover, OTA

Self-driving cars fuse three sensor types that disagree, encounter objects they cannot classify, hand control to humans with 10-second notice, and receive OTA updates mid-fleet. This page covers the edge cases and corner cases, and the dimensional model that handles them.

The core insight

Never discard the raw sensor detection. The fused output is a convenience; the raw detections are the truth. When the camera fails to see what lidar saw, that disagreement is the most valuable data point you have — it tells you the camera has a failure mode. Store both, keyed by a saga handover_id, and the warehouse becomes a training-data discovery engine.

For OTA, the model version is a dimension. Every perception detection carries a model_version_key. When a regression is found, the warehouse can answer "which cars are running the regressed model right now?" in milliseconds — and the safety service can issue a fleet-wide slow-down.

Edge cases

Sensor Fusion Disagreement
Problem

A self-driving car's lidar detects a pedestrian 30 m ahead; the camera does not (low light); the radar detects a metallic object but cannot classify it. The perception-fusion microservice must decide: is there a pedestrian? If it uses majority voting (2 of 3 say no), it suppresses the lidar detection. The car does not brake.

Impact

The car hits the pedestrian. The safety investigation reveals the three sensors disagreed, but the warehouse stored only the fused output — the individual sensor detections were discarded. The root cause (camera low-light failure) cannot be determined.

Dimensional solution

Store every sensor detection in fact_perception_detection with a dim_sensor_type (lidar, camera, radar, ultrasonic) and a confidence score. The fused output is a separate fact_fused_detection row that references the source detections. When sensors disagree, a fact_sensor_disagreement event is emitted with the disagreement type (classification, position, existence). The warehouse can answer "when did camera fail to detect what lidar saw?" as a SQL query.

Long-Tail Object Detection
Problem

The perception model has been trained on millions of images of cars, pedestrians and cyclists. But it encounters a person in a chicken suit riding a unicycle on a highway. The model classifies it as "unknown" with 0.3 confidence. The planner treats unknowns as stationary obstacles and brakes hard. A rear-end collision follows.

Impact

The car brakes for a non-threat, causing a rear-end collision. The warehouse stores the detection as "unknown" — there is no way to query "how often does the model encounter objects it cannot classify?" or "what are the most common unknown objects?"

Dimensional solution

Add a dim_detection_confidence dimension (high >0.9, medium 0.5–0.9, low <0.5, unknown). Add a fact_unknown_object table that stores the image crop (S3 URL), the model's top-5 predictions, and the human-verified label (filled in later by the data labelling team). The warehouse can answer "show me the 100 most common unknown objects in the last month" — feeding the next training cycle.

Human Handover Latency (L3→L2)
Problem

A Level 3 autonomous vehicle encounters a construction zone it cannot handle. It issues a handover request to the human driver. The human has 10 seconds to take control. But the handover-request microservice logs the request, while the human-response microservice logs the steering-wheel grab — in two separate services with unsynchronised clocks. The warehouse cannot determine the exact handover latency.

Impact

If the human takes 12 seconds (2 seconds too late), the car has already exited the construction zone in autonomous mode and collided with a cone. The safety investigation cannot prove the handover was late because the two event streams are in different services with 500 ms clock skew.

Dimensional solution

Use a saga coordinator that assigns a handover_id to the entire handover episode. Both services tag their events with handover_id and a monotonic sequence number. The warehouse stores fact_handover_episode with request_time, response_time, latency_ms, and outcome (success, timeout, abort). The clock skew is handled by the saga coordinator, which uses NTP-synced time and stores the skew estimate. Reproducibility is a query on handover_id.

Corner case: OTA Update Mid-Fleet with Perception Model Rollback

A fleet of 10,000 autonomous vehicles receives an OTA update to the perception model. Mid-rollout (3,000 cars updated), a regression is detected: the new model fails to detect emergency vehicles (fire trucks). The rollback must be issued, but 3,000 cars are already running the new model — some of them are driving.

OTA

3,000 cars have the new model; 7,000 have the old. The rollback must reach all 3,000 without bricking any car mid-drive.

Safety

Cars currently driving with the new model are at risk of hitting fire trucks. The safety service must issue an immediate geofence slow-down for all 3,000 cars.

Warehouse

The warehouse must track which cars have which model version at which timestamp, so that any future incident can be correlated with the model version.

Failure mode

A car with the new model approaches a fire truck at an intersection. The model does not detect it (regression). The car does not yield. The collision is recorded with the perception model version — but the OTA service has already started the rollback, so the warehouse shows the car running the new model at collision time. The rollback log and the collision log are in different services. The root cause (model regression) takes weeks to establish.

Solution

Every fact_perception_detection carries a model_version_key (dim_model_version with weights hash). The OTA service emits ota.started, ota.installed, ota.rollback_started, ota.rollback_completed events. The warehouse stores fact_ota_episode with car_key, old_version, new_version, start_time, end_time, and status. When a collision occurs, the query joins fact_collision to fact_ota_episode on (car_key, timestamp) to determine which model version was active. The safety service can query "which cars are running the regressed model right now?" and issue a fleet-wide slow-down in real time.

Dimensional model (SQL DDL)
-- Autonomous vehicle dimensional model
-- Handles sensor fusion, long-tail detection, handover, OTA rollback

CREATE TABLE dim_sensor_type (
  sensor_key    INT PRIMARY KEY,
  sensor_type   VARCHAR(20),  -- lidar, camera, radar, ultrasonic
  range_m       INT,
  resolution    VARCHAR(30),  -- e.g. "64 beams" or "1920x1080"
  failure_modes VARCHAR(100)  -- low-light, rain, fog, glare
);

CREATE TABLE dim_object_class (
  class_key     INT PRIMARY KEY,
  class_name    VARCHAR(50),
  is_threat     BOOLEAN,       -- pedestrian, vehicle = true; cone, bag = false
  training_count BIGINT        -- how many training examples
);

CREATE TABLE dim_model_version (
  version_key   INT PRIMARY KEY,
  version_tag   VARCHAR(20),   -- v2.3.1, v2.4.0
  weights_hash  VARCHAR(64),   -- SHA256 of model weights
  release_date  DATE,
  known_regressions TEXT       -- JSON array of known issues
);

CREATE TABLE dim_handover_cause (
  cause_key     INT PRIMARY KEY,
  cause         VARCHAR(30),   -- construction, weather, system-failure, geofence
  avg_latency_s DECIMAL(5,2)   -- historical average handover time
);

-- Fact: perception detection (every sensor detection stored)
CREATE TABLE fact_perception_detection (
  detection_key  BIGINT PRIMARY KEY,
  vehicle_key    INT,
  sensor_key     INT REFERENCES dim_sensor_type,
  class_key      INT REFERENCES dim_object_class,
  model_version_key INT REFERENCES dim_model_version,
  timestamp      TIMESTAMP,
  confidence     DECIMAL(5,4),
  distance_m     DECIMAL(8,2),
  bearing_deg    DECIMAL(6,2),
  is_fused       BOOLEAN,
  image_crop_url VARCHAR(500)  -- S3 URL for unknown objects
);

-- Fact: handover episode
CREATE TABLE fact_handover_episode (
  handover_key   BIGINT PRIMARY KEY,
  vehicle_key    INT,
  cause_key      INT REFERENCES dim_handover_cause,
  request_time   TIMESTAMP,
  response_time  TIMESTAMP,
  latency_ms     INT,
  outcome        VARCHAR(20),  -- success, timeout, abort
  driver_state   VARCHAR(20)   -- attentive, distracted, drowsy
);

-- Fact: OTA episode
CREATE TABLE fact_ota_episode (
  ota_key        BIGINT PRIMARY KEY,
  vehicle_key    INT,
  old_version_key INT REFERENCES dim_model_version,
  new_version_key INT REFERENCES dim_model_version,
  start_time     TIMESTAMP,
  end_time       TIMESTAMP,
  status         VARCHAR(20),  -- pending, installed, rollback-started, completed
  is_driving     BOOLEAN       -- was the car driving during update?
);
AV fleet analytics notebook
Run in the JupyterLite REPL to simulate a 50-vehicle fleet and compute sensor disagreement, unknown object and handover analytics.
# Autonomous Vehicle Fleet Analytics — JupyterLite Notebook
import numpy as np
import pandas as pd

np.random.seed(42)

# Simulate 50 AVs driving for 1 hour, 10 Hz sensor data
vehicles = [f"AV-{i:03d}" for i in range(50)]
n_rows = 36000 * 50  # 1 hour × 10 Hz × 50 vehicles (1.8M rows — lazy eval)

# For demo, generate 10 minutes × 50 vehicles = 300K rows
n_rows = 6000 * 50
data = {
    "timestamp": pd.date_range("2026-01-01", periods=6000, freq="100ms").repeat(50),
    "vehicle_id": np.tile(vehicles, 6000),
    "latitude": 37.7749 + np.random.randn(n_rows) * 0.005,
    "longitude": -122.4194 + np.random.randn(n_rows) * 0.005,
    "speed_ms": np.maximum(0, 15 + np.random.randn(n_rows) * 5),
    "accel_ms2": np.random.randn(n_rows) * 2,
    "automation_level": np.random.choice(["L2", "L3", "L4"], n_rows, p=[0.2, 0.5, 0.3]),
    "model_version": np.random.choice(["v2.3.1", "v2.3.2", "v2.4.0"], n_rows, p=[0.3, 0.4, 0.3]),
    "sensor_disagreement": np.random.choice([True, False], n_rows, p=[0.02, 0.98]),
    "unknown_objects": np.random.poisson(0.1, n_rows),
    "handover_requested": np.random.choice([True, False], n_rows, p=[0.001, 0.999]),
}
df = pd.DataFrame(data)

print("=== AV Fleet Summary ===")
print(f"Vehicles: {df['vehicle_id'].nunique()}")
print(f"Duration: 10 minutes @ 10 Hz")
print(f"Total rows: {len(df):,}")
print()

print("=== Automation Level Distribution ===")
print(df["automation_level"].value_counts(normalize=True).round(3))
print()

print("=== Model Version Distribution ===")
print(df["model_version"].value_counts(normalize=True).round(3))
print()

print("=== Sensor Disagreement Events ===")
disagree = df[df["sensor_disagreement"]]
print(f"Total disagreements: {len(disagree):,} ({len(disagree)/len(df)*100:.2f}%)")
print(f"Vehicles with disagreements: {disagree['vehicle_id'].nunique()}")
print()

print("=== Unknown Object Detections ===")
print(f"Total unknown objects: {df['unknown_objects'].sum():,}")
print(f"Vehicles with >5 unknowns: {(df.groupby('vehicle_id')['unknown_objects'].sum() > 5).sum()}")
print()

print("=== Handover Episodes ===")
handovers = df[df["handover_requested"]]
print(f"Total handover requests: {len(handovers)}")
print(f"By cause (simulated): construction=40%, weather=30%, system=20%, geofence=10%")

Microservices decomposition
  • perception-service — owns dim_sensor_type, dim_object_class, fact_perception_detection. Stores raw + fused detections.
  • handover-service — owns dim_handover_cause, fact_handover_episode. Saga-coordinated with monotonic sequence.
  • ota-service — owns dim_model_version, fact_ota_episode. Emits ota.started/installed/rollback events.
  • safety-service — owns fact_collision, fact_safety_event. Queries ota-service for model version at collision time.
