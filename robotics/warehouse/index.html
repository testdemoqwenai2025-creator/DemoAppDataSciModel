Warehouse robotics: deadlock, humans, inventory, fleet scaling

Warehouse fleets of 500+ AMRs face dining-philosophers deadlocks at intersections, human workers who stand in the way, inventory discrepancies between WMS and robot maps, and fleet scaling that breaks O(n²) algorithms. This page covers the edge cases and corner cases, and the dimensional model that handles them.

The core insight

A warehouse is a constrained environment with mixed traffic — robots, humans, conveyors, packages. The hardest modelling problem is not the robot; it is the disagreement between systems. The WMS says the bin is at A-3-7; the AMR says it is at B-2-1. The path planner says the aisle is clear; the perception service says there is a human. The dimensional answer: model the discrepancy as a first-class fact, not an error. The discrepancy table is where the warehouse learns about itself.

Edge cases

Multi-Robot Path Deadlock (Dining Philosophers)
Problem

Five AMRs (autonomous mobile robots) converge on a four-way intersection in a warehouse aisle. Each holds one aisle and requests the next. The path-planning microservice uses a greedy reservation system — each robot reserves its next cell. All five reserve, none can proceed. Classic dining philosophers deadlock.

Impact

All five robots freeze. Production stops. A human must walk to the intersection and manually move one robot. The warehouse loses 20 minutes of throughput. The warehouse stores path reservations but cannot detect the deadlock pattern — it just sees five robots stopped.

Dimensional solution

Add a dim_path_conflict_type dimension (deadlock, starvation, livelock, none). The path-planning service implements a deadlock detection algorithm (resource allocation graph) and emits a path.deadlock_detected event with the set of involved robots. The warehouse stores fact_path_conflict with the conflict type, the robot set (JSON array), the intersection coordinates, and the resolution action (wait, reroute, manual-intervention). Deadlock frequency per intersection becomes a queryable metric.

Dynamic Obstacle Insertion (Human Worker)
Problem

A human worker walks into an aisle that an AMR is traversing. The AMR's lidar detects the human and stops. But the human is standing still, looking at their clipboard. The AMR waits. After 30 seconds, the AMR's timeout fires and it requests a reroute. The reroute takes 5 seconds (computation). Meanwhile, the human has moved to the AMR's new path. The AMR stops again. Cycle repeats.

Impact

The AMR is stuck for 3 minutes, blocking the aisle. Other AMRs pile up behind it. The warehouse throughput drops 40% in that zone. The warehouse stores "human detected" events but cannot distinguish "human walking through" from "human standing in the way" — the resolution strategy is the same for both, and it is wrong for the latter.

Dimensional solution

Add a dim_human_behavior dimension (walking, standing, working, unknown). The perception service classifies the human's motion state (not just presence) using a short temporal window (3 seconds of tracking). fact_human_obstacle_event stores the behavior, the duration, the AMR's response (wait, reroute, request-assist), and the outcome (human-moved, am-rerouted, manual-clear). The warehouse can answer "which aisles have the most standing-human obstacles?" and redesign those aisles (add human walkways).

Inventory Discrepancy Reconciliation
Problem

An AMR picks a bin from location A-3-7 and moves it to B-2-1. The WMS (warehouse management system) updates its inventory: A-3-7 is empty, B-2-1 has the bin. But the AMR's internal map still shows the bin at A-3-7 (it has not received the WMS update). Another AMR goes to A-3-7 expecting a bin — finds nothing. It reports a "missing bin" error. The WMS and the AMR fleet disagree.

Impact

The missing-bin error triggers a cycle count (human inventory check). The human finds the bin at B-2-1, confirms the WMS is right, and the AMR fleet map is stale. The discrepancy takes 15 minutes to resolve. If this happens 100 times per shift, that is 25 hours of lost productivity.

Dimensional solution

Add a dim_inventory_state dimension (expected-present, expected-absent, actual-present, actual-absent, discrepancy). fact_inventory_event stores every pick, place and count with both the WMS expected state and the AMR observed state. When they disagree, a fact_inventory_discrepancy event is emitted with the discrepancy type (missing, unexpected, wrong-location), the time-to-resolve, and the root cause (stale-map, WMS-lag, sensor-error, theft). The warehouse can answer "what is our discrepancy rate by aisle and by shift?"

Corner case: Fleet Scaling from 50 → 500 Robots with Mixed Obstacle Types

A warehouse scales from 50 to 500 AMRs over 3 months. On day 1 of the 500-robot operation, a conveyor belt jams, spilling packages into the main thoroughfare. Simultaneously, 3 new human workers (unfamiliar with AMR protocols) walk into active aisles, and the WMS pushes a flash sale causing a 5× spike in pick missions.

Path planning

500 robots need deconfliction — the O(n²) algorithm that worked for 50 now takes 100× longer. Deadlocks cascade.

Perception

Spilled packages are dynamic obstacles that the perception model was not trained on. 3 humans in 3 different aisles create obstacle events simultaneously.

WMS

5× pick spike overwhelms the WMS → AMR map sync. Inventory discrepancies spike. The fact_inventory_discrepancy table grows 10× faster than expected.

Failure mode

The path-planning service falls behind — robots stop moving because they cannot get deconfliction clearances. The perception service misclassifies spilled packages as "human" (both are non-map obstacles), triggering unnecessary emergency stops. The WMS sync lag causes 200 inventory discrepancies in 1 hour. The warehouse effectively shuts down. The warehouse stores all events but cannot correlate them — the path, perception and WMS services have no shared key.

Solution

A saga coordinator assigns a fleet_event_key to the entire incident (conveyor jam + human intrusions + pick spike). All three services tag their events with the fleet_event_key. The warehouse stores fact_fleet_event with start, peak, resolution, and impact (throughput loss, robot-hours lost, discrepancies caused). The path-planning service is upgraded to a hierarchical deconfliction (zone-level first, robot-level second) — O(n log n) instead of O(n²). The perception service is retrained with spilled-package images. The WMS sync is upgraded to event-sourced (CQRS) so the AMR map updates in real time. The warehouse can answer "what caused the throughput drop on day 1 of 500-robot operation?" as a single query on fleet_event_key.

Dimensional model (SQL DDL)
-- Warehouse robotics dimensional model
-- Handles path deadlock, human obstacles, inventory discrepancy, fleet scaling

CREATE TABLE dim_path_conflict_type (
  conflict_key  INT PRIMARY KEY,
  conflict_type VARCHAR(20),  -- deadlock, starvation, livelock, none
  detection_algo VARCHAR(30), -- resource-graph, timeout, cycle-detection
  severity       VARCHAR(20)  -- minor, moderate, severe
);

CREATE TABLE dim_human_behavior (
  behavior_key  INT PRIMARY KEY,
  behavior      VARCHAR(20),  -- walking, standing, working, unknown
  avg_duration_s INT,
  amr_response  VARCHAR(20)   -- wait, reroute, request-assist
);

CREATE TABLE dim_inventory_state (
  state_key     INT PRIMARY KEY,
  wms_state     VARCHAR(20),  -- expected-present, expected-absent
  amr_state     VARCHAR(20),  -- actual-present, actual-absent
  is_discrepancy BOOLEAN
);

CREATE TABLE dim_fleet_event (
  fleet_event_key INT PRIMARY KEY,
  event_type    VARCHAR(30),  -- conveyor-jam, human-intrusion, pick-spike
  start_time    TIMESTAMP,
  peak_time     TIMESTAMP,
  end_time      TIMESTAMP,
  throughput_loss_pct DECIMAL(5,2),
  robot_hours_lost DECIMAL(8,2)
);

-- Fact: path conflict
CREATE TABLE fact_path_conflict (
  conflict_key  BIGINT PRIMARY KEY,
  robot_set     TEXT,          -- JSON array of robot IDs involved
  conflict_type_key INT REFERENCES dim_path_conflict_type,
  intersection_x DECIMAL(8,2),
  intersection_y DECIMAL(8,2),
  timestamp     TIMESTAMP,
  duration_s    INT,
  resolution    VARCHAR(20),   -- wait, reroute, manual
  fleet_event_key INT          -- NULL unless part of a fleet event
);

-- Fact: human obstacle event
CREATE TABLE fact_human_obstacle_event (
  obstacle_key  BIGINT PRIMARY KEY,
  robot_key     INT,
  behavior_key  INT REFERENCES dim_human_behavior,
  aisle_key     INT,
  timestamp     TIMESTAMP,
  duration_s    INT,
  outcome       VARCHAR(20),   -- human-moved, am-rerouted, manual-clear
  fleet_event_key INT
);

-- Fact: inventory discrepancy
CREATE TABLE fact_inventory_discrepancy (
  discrepancy_key BIGINT PRIMARY KEY,
  location_key  INT,
  state_key     INT REFERENCES dim_inventory_state,
  discrepancy_type VARCHAR(20), -- missing, unexpected, wrong-location
  root_cause    VARCHAR(20),    -- stale-map, WMS-lag, sensor-error, theft
  timestamp     TIMESTAMP,
  time_to_resolve_s INT,
  resolution    VARCHAR(20),    -- cycle-count, auto-correct, escalate
  fleet_event_key INT
);
Warehouse fleet analytics notebook
Run in the JupyterLite REPL to simulate a 200-AMR warehouse and compute path conflict, human obstacle, inventory discrepancy and throughput analytics.
# Warehouse Robotics Fleet Analytics — JupyterLite Notebook
import numpy as np
import pandas as pd

np.random.seed(42)

# Simulate 200 AMRs operating for 8 hours, 1 Hz fleet state
robots = [f"AMR-{i:03d}" for i in range(200)]
n_rows = 28800 * 200  # 8 hours × 1 Hz × 200 robots (5.76M — lazy eval)
# For demo: 1 hour × 200 = 720K rows
n_rows = 3600 * 200

data = {
    "timestamp": pd.date_range("2026-01-01", periods=3600, freq="1s").repeat(200),
    "robot_id": np.tile(robots, 3600),
    "x_m": np.random.rand(n_rows) * 200,
    "y_m": np.random.rand(n_rows) * 100,
    "battery_pct": np.maximum(0, 80 + np.random.randn(n_rows) * 15),
    "speed_ms": np.maximum(0, 1.5 + np.random.randn(n_rows) * 0.5),
    "task": np.random.choice(["pick", "place", "transit", "idle", "charging"], n_rows, p=[0.35, 0.2, 0.25, 0.15, 0.05]),
    "path_conflict": np.random.choice([True, False], n_rows, p=[0.005, 0.995]),
    "human_obstacle": np.random.choice([True, False], n_rows, p=[0.01, 0.99]),
    "inventory_discrepancy": np.random.choice([True, False], n_rows, p=[0.002, 0.998]),
}
df = pd.DataFrame(data)

print("=== Warehouse Fleet Summary ===")
print(f"Robots: {df['robot_id'].nunique()}")
print(f"Duration: 1 hour @ 1 Hz = {len(df):,} rows")
print()

print("=== Task Distribution ===")
print(df["task"].value_counts(normalize=True).round(3))
print()

print("=== Path Conflicts (Deadlock Detection) ===")
conflicts = df[df["path_conflict"]]
print(f"Total path conflicts: {len(conflicts)}")
print(f"Conflicts per robot: {len(conflicts) / df['robot_id'].nunique():.1f}")
# Robots with most conflicts
top_conflict = conflicts.groupby("robot_id").size().sort_values(ascending=False).head(5)
print("Top 5 robots by conflict count:")
print(top_conflict)
print()

print("=== Human Obstacle Events ===")
humans = df[df["human_obstacle"]]
print(f"Total human obstacle events: {len(humans)}")
print(f"Aisles affected: {humans['x_m'].nunique()}")
print()

print("=== Inventory Discrepancies ===")
disc = df[df["inventory_discrepancy"]]
print(f"Total discrepancies: {len(disc)}")
print(f"Discrepancy rate: {len(disc)/len(df)*100:.3f}%")
print()

print("=== Battery Distribution ===")
battery = df.groupby("robot_id")["battery_pct"].mean()
print(f"  Mean: {battery.mean():.1f}%")
print(f"  Min:  {battery.min():.1f}%")
print(f"  Robots <20%: {(battery < 20).sum()}")
print()

print("=== Throughput Analysis ===")
active = df[df["task"].isin(["pick", "place"])]
print(f"Active pick/place operations: {len(active):,}")
print(f"Throughput: {len(active)/60:.0f} ops/min")

Microservices decomposition
  • path-planning-service — owns dim_path_conflict_type, fact_path_conflict. Hierarchical deconfliction (O(n log n)).
  • perception-service — owns dim_human_behavior, fact_human_obstacle_event. Classifies human motion state.
  • inventory-service — owns dim_inventory_state, fact_inventory_discrepancy. Reconciles WMS vs AMR maps.
  • fleet-event-service — owns dim_fleet_event. Saga coordinator for multi-cause incidents.
