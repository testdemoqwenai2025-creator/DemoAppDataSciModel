Enterprise Architecture

Conformed dimensions

Conformed dimensions are the keystone of an enterprise Kimball warehouse. They are dimensions designed once, mastered once and reused across every fact table that needs them — enabling drill-across analytics, consistent labelling and integrated enterprise reporting.

What makes a dimension “conformed”

A dimension is conformed when multiple fact tables can use it as if it were a single shared dimension. In practice this means three things must align:

  1. Shared surrogate keys — the same dimension key resolves to the same row in every fact table.
  2. Shared attribute labels and hierarchies — the labels and rollups mean the same thing everywhere they appear.
  3. Shared business glossary definition — the dimension and each attribute have a single, owned definition in the business glossary.

When all three hold, any two fact tables that share the dimension can be queried together using that dimension. This is the drill-across capability that turns a collection of data marts into an enterprise warehouse.

dim_customer

A master dimension that captures every customer across every channel. Conformance enables customer 360° analytics across sales, service, returns and marketing.

  • Customer → Acquisition Channel → Region
dim_product
Type 2
Type 2 — track changes to category, brand, cost, price

The product master, including SKU, category and brand hierarchies. Conformance ensures sales, inventory and returns all use the same product identity.

Hierarchies
  • SKU → Subcategory → Category → Department
  • SKU → Brand → Manufacturer
dim_store
Type 2
Type 2 — track changes to format, region, ownership

Physical and digital locations where transactions occur. Conformance enables consistent territory reporting across all fact tables.

Hierarchies
  • Store → District → Region → Country
  • Store → Format → Channel
dim_employee
Type 2
Type 2 — track changes to role, manager, department

The workforce dimension, used in sales attribution, service and finance. Conformance links employee performance consistently across processes.

Hierarchies
  • Employee → Team → Department → Division
  • Employee → Manager → Director → VP
dim_geography
Type 1
Type 1 — geographic boundaries are correctable

A geographic reference dimension that supports multiple hierarchies (political, postal, sales territory). Often referenced by other dimensions as well as facts.

Hierarchies
  • City → Region → Country → Continent
  • Postcode → District → Region → Country

Slowly Changing Dimensions

Dimension attributes change over time. Kimball defines four patterns for handling that change. The choice is made per attribute, not per dimension — a single dimension can mix types.

Type 1
Overwrite

The old value is replaced with the new value. No history is kept. Use for corrections, or for attributes where history is not analytically useful.

Example

Correcting a misspelled customer name. Updating a product subcategory that was misclassified.

Type 2
Track history

A new row is inserted with a new surrogate key, and the old row is closed out with an effective_to date. Use for attributes where change history drives analytics.

Example

Customer segment change from “Standard” to “Premium” on a known date. Product reclassification.

Type 3
Limited history

Two columns hold the current and previous value of an attribute. Use when only the immediately-prior value matters, not the full history.

Example

Customer’s current region and previous region — useful for region-transfer analysis.

Type 6
Hybrid (1+2+3)

Combines Type 1, 2 and 3: a current-value column (Type 1), historical rows (Type 2), and a original-value column (Type 3). Use when you need both “as was” and “as is” reporting.

Example

Reporting sales by the customer’s current segment (Type 1 view) and by the segment at the time of sale (Type 2 view) from the same dimension.

Outriggers and snowflakes

An outrigger is a dimension referenced from another dimension — for example, a geography dimension referenced from the store dimension. Outriggers are permitted in Kimball when they simplify maintenance and the outrigger is itself conformed. They are used sparingly, because every hop away from the fact table adds BI complexity.

A snowflake is the more aggressive form: normalising the dimension into multiple related tables. Snowflakes are generally avoided in this solution in favour of denormalised stars, unless there is a clear storage or maintenance benefit. Any snowflake is documented in the model specification so the BI semantic layer can flatten it transparently for end users.
