Physics: singularities, metric tensors, arbitrary precision

Physics data modelling fails at the extremes. Near a black hole, coordinates become singular. On curved spacetime, the metric tensor is not Euclidean. At the Planck scale, float64 underflows. This page covers the edge cases and corner cases, and the dimensional model that handles them — coordinate systems as dimensions, metric tensors as dimensions, precision as a dimension.

The core insight

In physics, the coordinate system is not neutral. Schwarzschild coordinates have a singularity at the event horizon that is not physical — it is an artifact of the coordinate choice. Kruskal-Szekeres coordinates remove it. The dimensional answer: store the coordinate system as a dimension, not as an implicit assumption. The fact row carries the coordinate system key; queries can transform between systems.

Similarly, precision is a dimension. A float64 result near the Planck scale is meaningless; a float128 result is borderline; an arbitrary-precision result is reproducible. Store all three, keyed by a dim_precision dimension, and let the query choose. This turns "we got NaN" into "we got float64-NaN, float128-1.6e-35, arbitrary-1.6162e-35" — three rows, three precisions, one event.

Edge cases

Two physics sub-domains, two data-modelling failures, two dimensional solutions.

Scale Transitions & Coordinate Singularities
Physics
Problem

A physical simulation microservice passes spatial coordinates to a quantum mechanics or relativity service, causing runtime errors due to floating-point truncation at the Planck scale (10⁻³⁵m) or division-by-zero boundaries near gravitational singularities (black hole modelling).

Impact

A general-relativity simulation near a black hole event horizon passes coordinates to a quantum-field service. The Schwarzschild metric has a coordinate singularity at r=2M (the horizon). Standard float64 produces inf or NaN; the fact table stores garbage; downstream analysis crashes.

Dimensional solution

Add a dim_coordinate_system dimension (Cartesian, spherical, Schwarzschild, Kerr, Kruskal-Szekeres) and a dim_scale_regime dimension (classical, relativistic, quantum, Planck). Fact rows near singularities carry a precision_tier (float64, float128, arbitrary-precision decimal). Use Kruskal-Szekeres coordinates (which remove the horizon singularity) for storage; transform to Schwarzschild on query. The precision_tier lets you query "give me the high-precision results near the horizon" without scanning every row.

Arbitrary Precision & Non-Euclidean Metrics
Mathematics
Problem

Microservices evaluating complex topologies or non-Euclidean geometries pass geospatial data to an analytics service using standard Cartesian floating-point vectors (R³), triggering systematic spatial drift and metric tensor breakdown.

Impact

A general-relativity simulation on a curved spacetime manifold passes 4-vectors to an analytics service that assumes Euclidean inner products. The metric tensor g_μν is not δ_μν; dot products return wrong values; geodesic integration drifts. After 1000 timesteps, the particle is light-years off course.

Dimensional solution

Store the metric tensor g_μν alongside every 4-vector as a dim_metric dimension (Minkowski, Schwarzschild, FLRW, Kerr). Fact rows carry both the vector components and the metric_key. The analytics service computes inner products as g_μν v^μ w^ν, not δ_μν v^μ w^ν. For arbitrary precision, use a dim_precision tier and store the Rust rug BigDecimal result alongside the float64 result for reproducibility.

Corner case: The High-Energy Quantum Event Horizon

A simulation tracks a relativistic particle accelerating near a black hole event horizon while simultaneously experiencing quantum entanglement with an outside reference framework.

Relativity

Coordinate systems approaching spatial infinity — the particle near the horizon is in Kruskal coordinates, the outside observer is in Schwarzschild, and the two must be reconciled

Quantum

Maintain quantum superposition matrix states spanning multiple non-local nodes — the entangled partner is outside the horizon, so the state vector is split across two microservices

Computation

Process arbitrary-precision floating decimals without losing state-synchronisation frames across the microservice mesh — the geodesic integrator needs 128-bit, the entanglement calculator needs arbitrary precision

Failure mode

The relativity service computes the particle position in Kruskal coordinates at 128-bit precision. The quantum service holds the entangled state as a complex matrix at arbitrary precision. The two services cannot agree on a shared time coordinate — relativistic time dilation means "now" is frame-dependent. The saga coordinator cannot commit because the two services disagree on whether the entanglement measurement happened before or after the horizon crossing.

Solution

Introduce a dim_observer_frame dimension and a dim_cauchy_surface dimension (the spacelike hypersurface on which the state is defined). The saga coordinator assigns a single cauchy_surface_key to the entangled measurement event. Both services project their state onto that Cauchy surface before committing. The fact_entanglement_event table stores both the relativistic (128-bit) and quantum (arbitrary-precision) results, linked by the cauchy_surface_key. Reproducibility is a SQL join on that key — not an argument about simultaneity.

Dimensional model (SQL DDL)
Coordinate system, scale regime, precision tier, metric tensor and observer frame as dimensions. Handles singularities, non-Euclidean geometry and arbitrary precision.
-- Physics & mathematics dimensional model
-- Handles coordinate singularities, metric tensors, arbitrary precision

-- Coordinate system dimension (handles singularities)
CREATE TABLE dim_coordinate_system (
  coord_sys_key     INT PRIMARY KEY,
  name              VARCHAR(50),   -- Cartesian, spherical, Schwarzschild, Kerr, Kruskal
  dimensionality    SMALLINT,      -- 3, 4, or higher
  has_singularity   BOOLEAN,       -- true for Schwarzschild at r=2M
  singularity_type  VARCHAR(30),   -- coordinate (removable) or physical (essential)
  transform_to      VARCHAR(50)    -- preferred non-singular coords for storage
);

-- Scale regime dimension (classical → quantum → Planck)
CREATE TABLE dim_scale_regime (
  scale_key         INT PRIMARY KEY,
  regime            VARCHAR(20),   -- classical, relativistic, quantum, Planck
  length_scale_m    DECIMAL(20,8), -- typical length (Planck = 1.6e-35)
  energy_scale_j    DECIMAL(20,8),
  requires_qm       BOOLEAN,
  requires_gr       BOOLEAN
);

-- Precision tier dimension
CREATE TABLE dim_precision (
  precision_key     INT PRIMARY KEY,
  tier              VARCHAR(20),   -- float64, float128, arbitrary
  bits              INT,           -- 64, 128, or NULL for arbitrary
  library           VARCHAR(30)    -- IEEE754, quadmath, rug (Rust), mpmath (Python)
);

-- Metric tensor dimension (non-Euclidean geometry)
CREATE TABLE dim_metric (
  metric_key        INT PRIMARY KEY,
  name              VARCHAR(50),   -- Minkowski, Schwarzschild, FLRW, Kerr
  signature         VARCHAR(10),   -- (-,+,+,+) or (+,+,+) etc.
  components_json   TEXT,          -- g_munu as JSON matrix
  is_flat           BOOLEAN,       -- true for Minkowski
  curvature         VARCHAR(20)    -- zero, positive, negative
);

-- Observer / reference frame dimension
CREATE TABLE dim_observer_frame (
  observer_key      INT PRIMARY KEY,
  frame_type        VARCHAR(30),   -- inertial, accelerating, comoving, stationary
  velocity_fraction DECIMAL(10,8), -- v/c
  is_comoving       BOOLEAN        -- true for cosmological comoving frame
);

-- Fact: spacetime event (handles singularities via coord system)
CREATE TABLE fact_spacetime_event (
  event_key         BIGINT PRIMARY KEY,
  coord_sys_key     INT REFERENCES dim_coordinate_system,
  scale_key         INT REFERENCES dim_scale_regime,
  precision_key     INT REFERENCES dim_precision,
  metric_key        INT REFERENCES dim_metric,
  observer_key      INT REFERENCES dim_observer_frame,
  t_coordinate      DECIMAL(20,8),
  r_coordinate      DECIMAL(20,8),  -- high precision near horizon
  theta             DECIMAL(20,8),
  phi               DECIMAL(20,8),
  workflow_run_key  INT,
  is_near_singularity BOOLEAN,
  precision_upgrade  BOOLEAN       -- true if arbitrary-precision was needed
);

-- Fact: geodesic step (handles non-Euclidean metrics)
CREATE TABLE fact_geodesic_step (
  step_key          BIGINT PRIMARY KEY,
  metric_key        INT REFERENCES dim_metric,
  coord_sys_key     INT REFERENCES dim_coordinate_system,
  precision_key     INT REFERENCES dim_precision,
  position_4vec     TEXT,          -- JSON: [t, r, theta, phi]
  velocity_4vec     TEXT,          -- JSON: [dt, dr, dtheta, dphi]
  proper_time       DECIMAL(20,8),
  affine_param      DECIMAL(20,8),
  step_count        BIGINT,
  drift_error       DECIMAL(15,8)  -- estimated integration error
);
Microservices decomposition
  • relativity-service — owns dim_coordinate_system, dim_metric, fact_spacetime_event. Computes in Kruskal coordinates; stores 128-bit near horizons.
  • quantum-service — owns dim_scale_regime, fact_entanglement_event. Holds superposition states as complex matrices; uses arbitrary precision.
  • precision-service — owns dim_precision. Provides float64/float128/arbitrary-precision computation as a shared utility.
  • saga-coordinator — assigns cauchy_surface_key; commits the entanglement fact only when relativity and quantum services agree on the Cauchy surface.
