Genomics data pipelines — VCF to clinical-trial cohort

DSModelPro's genomics pipeline covers the full journey from raw variant calls (VCF/BGEN) through QC, phasing, imputation, GWAS, and clinical-trial participant identification. Built on GA4GH standards and FAIR principles, with PLINK2/bcftools/Minimac4 templates ready to deploy.

The genomics data engineering challenge

A genomics data pipeline processes variant calls from sequencing or genotyping arrays through six stages: raw VCF ingestion, sample & variant QC, phasing, imputation, post-imputation QC, and GWAS / cohort selection. Each stage has its own tooling, file formats, and failure modes — and each stage must be reproducible, FAIR-compliant, and auditable.

The dimensional model below treats variants and samples as conformed dimensions. One fact_genotype_call row per variant-sample pair. This lets you query "which samples carry this variant?", "which variants are in this gene?", or "which participants meet this trial's eligibility criteria?" — all from one warehouse, without re-running the pipeline.

The six-stage genomics pipeline

From raw VCF to clinical-trial cohort. Each stage is a discrete step with its own tools and outputs.

1. Raw VCF / BGEN

Receive variant calls from sequencing or genotyping arrays. Validate format, check contigs, normalise multi-allelics.

bcftools, PLINK2
2. Sample & variant QC

Filter by missingness (--geno, --mind), Hardy-Weinberg equilibrium, sex-check discordance, heterozygosity outliers, ancestry PCA.

PLINK2, QCtools
3. Phasing

Estimate haplotypes from unphased genotypes. Required before imputation. Outputs phased VCF or binary format.

shapeit4, Eagle
4. Imputation

Infer missing genotypes using a reference panel (1000G, TOPMed, HRC). Outputs dosages in BGEN or VCF format with per-variant R².

Minimac4, Beagle 5.4
5. Post-imputation QC

Filter imputed variants by R² > 0.3, INFO > 0.8. Remove variants with low imputation confidence. Build analysis-ready dataset.

PLINK2, bcftools
6. GWAS / cohort selection

Run association tests, build Manhattan plots, select clinical-trial participants by eligibility criteria.

PLINK2, REGENIE, SAIGE

Bioinformatics file standards

Five formats cover 95% of genomics data engineering. Each has a different purpose — VCF for raw calls, BGEN for imputed dosages, PLINK for GWAS.

VCF
.vcf, .vcf.gz
Variant Call Format

Text-based (tab-delimited) format for variant calls. Standard since 2010. Supports multi-allelic, phased genotypes, and genotype likelihoods.

Use: Raw sequencing output, pre-imputation
BGEN
.bgen
Binary GENotype

Binary format for imputed genotype dosages. Compressed, indexed, supports probability distributions. UK Biobank standard.

Use: Post-imputation, large biobanks
PLINK BED
.bed, .bim, .fam
PLINK Binary

Binary trio for genotype data. Fast random access. The de facto standard for GWAS tooling since 2007.

Use: GWAS, QC, population genetics
PGEN
.pgen, .pvar, .psam
PLINK2 Binary

PLINK2 successor. Supports dosages (not just hard calls), multi-allelics, and is more compact than BED.

Use: Modern GWAS, dosage-aware analyses
BCF
.bcf
Binary VCF

Binary representation of VCF. Indexed with Tabix. Faster than gzipped VCF for large cohorts.

Use: Large-scale sequencing studies

GA4GH standards — Global Alliance for Genomics & Health
GA4GH defines the API and data standards that make genomics interoperable across institutions. DSModelPro's warehouse exposes dim_variant.vrs_id for VRS-compliant variant identification.
Beacon

Federated query API for genomic variants. "Does this dataset contain this variant?" without exposing individual data. Beacon v2 supports cohorts and individuals.

htsget

Standardised REST API for streaming VCF, BAM, CRAM, and other HTS formats. Enables federated access without full-file download.

refget

Standard for identifying reference sequences by content (SHA-512 truncation). Ensures consistent reference genome identification across systems.

VRS

Variation Representation Standard. Normalised model for representing genetic variants independent of nomenclature (HGVS, VCF, SPDI all map to VRS).

Phenopackets

Standard for sharing phenotype and clinical data linked to genomic data. FHIR-compatible. Used for rare disease and cancer.

Service Info

Standardised endpoint (/service-info) describing a GA4GH-compliant service. Enables discovery and interoperability.

FAIR principles — Findable, Accessible, Interoperable, Reusable
How DSModelPro applies FAIR to genomics data. Required by most government and academic funders.
FFindable

Variants, samples, and cohorts have persistent identifiers (DOIs, ORCID, GA4GH IDs). Metadata is registered in searchable resources (EGA, dbGaP, Beacon).

AAccessible

Data accessible via standardised protocols (htsget, Beacon API). Controlled-access for sensitive data (EGA, dbGaP). Open-access for reference panels.

IInteroperable

Common formats (VCF, BGEN, PGEN) and ontologies (HGNC, HPO, MONDO, EFO). GA4GH APIs for cross-system queries. VRS for variant normalisation.

RReusable

Clear licences (CC0, CC-BY, controlled-access agreements). Provenance tracked via W3C PROV or RO-Crate. QC reports attached to datasets.

Dimensional model for genomics (SQL DDL)
7 tables: dim_variant, dim_sample, dim_cohort, dim_eligibility_criteria, fact_genotype_call (partitioned), fact_eligibility_assessment, fact_gwas_result. VRS-compliant variant IDs. SCD2-safe eligibility snapshots.
-- Genomics warehouse star schema
-- Designed for variant × sample × genotype queries at biobank scale

CREATE TABLE dim_variant (
  variant_key          BIGINT PRIMARY KEY,
  chrom                SMALLINT NOT NULL,
  position             BIGINT NOT NULL,
  rsid                 VARCHAR(20),
  ref_allele           CHAR(1) NOT NULL,
  alt_allele           CHAR(1) NOT NULL,
  -- GA4GH VRS identifier (normalised variant representation)
  vrs_id               VARCHAR(100),
  -- Quality metrics from QC pipeline
  maf                  DECIMAL(6,4),
  hwe_pvalue           DECIMAL(10,8),
  imputation_r2        DECIMAL(4,3),  -- NULL for typed variants
  info_score           DECIMAL(4,3),
  qc_status            VARCHAR(20),   -- PASS, FAIL_MISSINGNESS, FAIL_HWE, etc.
  UNIQUE (chrom, position, ref_allele, alt_allele)
);

CREATE TABLE dim_sample (
  sample_key           BIGINT PRIMARY KEY,
  participant_id       VARCHAR(50) NOT NULL,
  cohort_id            VARCHAR(20),   -- UKB, 1000G, TOPMED, etc.
  ancestry             VARCHAR(10),   -- EUR, AFR, EAS, SAS, AMR
  sex                  CHAR(1),       -- M, F
  -- QC flags
  sex_check_discordant BOOLEAN,
  heterozygosity_outlier BOOLEAN,
  ancestry_pca_outlier BOOLEAN,
  qc_status            VARCHAR(20),
  -- Consent / governance
  consent_code         VARCHAR(20),
  access_tier          SMALLINT,      -- 0=open, 1=controlled, 2=registered
  UNIQUE (participant_id)
);

CREATE TABLE dim_cohort (
  cohort_key           SMALLINT PRIMARY KEY,
  cohort_id            VARCHAR(20) NOT NULL,
  description          TEXT,
  n_participants       INTEGER,
  access_type          VARCHAR(20),   -- OPEN, CONTROLLED, REGISTERED
  licence              VARCHAR(100),
  UNIQUE (cohort_id)
);

CREATE TABLE dim_eligibility_criteria (
  criteria_key         BIGINT PRIMARY KEY,
  trial_id             VARCHAR(50) NOT NULL,    -- e.g. NCT04512345
  criteria_name        VARCHAR(200),
  criteria_type        VARCHAR(50),             -- INCLUSION, EXCLUSION
  -- Structured criteria (parsed from free text via NLP)
  phenotype_code       VARCHAR(50),             -- HPO, MONDO, ICD-10
  min_age              INTEGER,
  max_age              INTEGER,
  biomarker_threshold  DECIMAL(10,4),
  biomarker_operator   VARCHAR(5),              -- >, <, =, BETWEEN
  UNIQUE (trial_id, criteria_name)
);

CREATE TABLE fact_genotype_call (
  variant_key          BIGINT NOT NULL REFERENCES dim_variant,
  sample_key           BIGINT NOT NULL REFERENCES dim_sample,
  -- Dosage: 0.0 to 2.0 (imputed) or 0/1/2 (typed)
  dosage               DECIMAL(4,3) NOT NULL,
  genotype             SMALLINT,     -- 0, 1, 2 (hard call from dosage)
  -- Quality
  genotype_probability DECIMAL(6,5),  -- GP field from BGEN
  depth                SMALLINT,      -- DP from VCF (NULL if imputed)
  -- Partitioning
  partition_date       DATE NOT NULL,
  PRIMARY KEY (variant_key, sample_key)
) PARTITION BY RANGE (partition_date);

CREATE TABLE fact_eligibility_assessment (
  assessment_key       BIGINT PRIMARY KEY,
  participant_key      BIGINT NOT NULL REFERENCES dim_sample,
  trial_id             VARCHAR(50) NOT NULL,
  criteria_key         BIGINT NOT NULL REFERENCES dim_eligibility_criteria,
  eligible             BOOLEAN NOT NULL,
  assessed_at          TIMESTAMP NOT NULL,
  -- Snapshot of the criteria at assessment time (SCD2-safe)
  criteria_snapshot    JSONB
);

CREATE TABLE fact_gwas_result (
  result_key           BIGINT PRIMARY KEY,
  variant_key          BIGINT NOT NULL REFERENCES dim_variant,
  phenotype            VARCHAR(100) NOT NULL,  -- e.g. 'T2D', 'height'
  cohort_key           SMALLINT NOT NULL REFERENCES dim_cohort,
  beta                 DECIMAL(8,4),
  se                   DECIMAL(8,4),
  pvalue               DECIMAL(10,8),
  neglog10_p           DECIMAL(6,3),
  n_cases              INTEGER,
  n_controls           INTEGER,
  effect_allele        CHAR(1),
  assessed_at          TIMESTAMP NOT NULL
);

Agent-queryable genomics warehouse

The same agent-queryable data layer pattern applies here. A clinical-trial-matching agent can query dim_variant × dim_sample via a machine-readable data contract — “find all participants eligible for trial NCT-04512345, with genotype evidence” — and receive a governed, bias-checked, audited answer. The agent never writes SQL; it queries the contract. See the full pattern on /fact-tables, including an interactive demo.
