Hypothetical Scenario

Distributed scientific computing: a multi-domain platform

A hypothetical federated platform serving climate modelling, genomics and multi-messenger astrophysics. Three scientific domains, one dimensional spine. The platform demonstrates that the same conformed dimensions — Date, Site, Sample, Workflow Run, Compute Environment — serve radically different scientific workloads, with provenance as the unifying first-class concern.

Follow a published figure through lineage recovery, re-run, and statistical diff.
Why three domains, not one

Building a platform for one scientific domain is tempting but produces a domain-specific tool that cannot outlive its funding cycle. Building for three forces the architecture to find the common spine — the dimensional shapes that are invariant across climate, genomics and astrophysics. That spine is: experiment × run × sample × variable × time × provenance. Once you have it, the fourth domain is a configuration exercise, not a rebuild.

The hard-won insight is that provenance is the dimensional shape that distinguishes scientific data from commercial data. A retailer does not need to know which compiler produced last quarter’s sales figure. A climate scientist absolutely needs to know which model version, which forcing dataset and which compute environment produced a temperature projection. Provenance dimensions are not optional in this platform — they are conformed.

The three scientific domains

Each domain has different volume, velocity and variety — but the same dimensional spine.

Transient alerts must land in the warehouse within 30 seconds so follow-up observations can be scheduled. The fact table is written from the alert stream (lambda architecture); the slow-stream backfill reconciles with the calibrated survey catalogue.

Platform architecture for scientific workloads
Instruments and simulations submit to a workflow orchestrator (Nextflow / Argo / CWL). Pipelines run on HPC or k8s batch, write artifacts to object storage, register their run with the provenance service, and emit observations to the event broker. The warehouse consumes both the events (fast path) and the provenance dimensions (slow path).

Data flow

Provenance dimensions — the scientific spine

Four conformed dimensions capture the lineage of every measurement. Together they answer “who ran what, with what inputs, on what infrastructure, when” — the minimum required for reproducibility.

dim_workflow_run

One row per pipeline execution: pipeline name, version, commit hash, container image, parameters hash, submitter, start/end timestamps, exit status.

dim_compute_environment

One row per compute environment: scheduler (Slurm/PBS/k8s), queue, node count, CPU/GPU type, memory, network fabric. Captures the “where” of every computation.

dim_input_dataset

One row per input dataset: DOI or internal ID, version, checksum, source repository, license. Captures the “what was consumed” of every computation.

dim_software_artifact

One row per software artifact: package name, version, container image digest, dependencies hash. Captures the “with what” of every computation.

FAIR data principles — platform support

Findable, Accessible, Interoperable, Reusable. Each principle maps to concrete platform capabilities, not aspiration.

LetterPrincipleHow the platform supports it
FFindableThe catalog-service indexes every data product with a persistent identifier (DOI or internal ARK). Search includes domain, variable, geographic bounding box, time range and workflow lineage.
AAccessibleData products are served via open protocols (S3 for objects, TAP for tabular, VOEvent for alerts). Access control is enforced at the query-federation service; public products need no auth.
IInteroperableDomain vocabularies are mapped to community standards: CF conventions for climate, GA4GH for genomics, VOtable for astronomy. The conformed dimensions carry the standard terms alongside internal labels.
RReusableEvery data product carries a license, a citation, and a provenance trail linking to dim_workflow_run, dim_compute_environment and dim_input_dataset. Reuse is a query away.

Workflow orchestration

Three orchestrators cover the spectrum from HPC batch to cloud-native workflows. The platform supports all three because scientific communities have already invested in their tooling — fighting that is a losing battle.

Nextflow
Genomics, bioinformatics

Domain-standard in genomics. Pipeline definitions are version-controlled Groovy scripts; runs are reported to the provenance service via a Nextflow plugin that emits workflow.completed events.

Argo Workflows
k8s-native, climate & astro

Cloud-native workflow engine for Kubernetes. Each step is a container; the platform injects sidecars that capture stdout/stderr, resource usage and exit code into the provenance dimensions automatically.

CWL / Pegasus
HPC, large-scale simulations

Common Workflow Language and Pegasus for HPC environments where Slurm/PBS rule. The platform bridges to HPC via a submit-side adapter that translates the run manifest into provenance events.

Reproducibility as a query

The acid test of a scientific platform is: given a published result, can I re-run the exact computation that produced it? In this platform, the answer is yes, and it is a single query.

A published figure cites a workflow_run_key. Joining that key to dim_workflow_run, dim_compute_environment, dim_input_dataset and dim_software_artifact recovers the full lineage. A templated re-submission to the orchestrator produces a fresh run with the same inputs — and the new run’s outputs can be diffed against the originals to verify bit-wise reproducibility (or, more realistically, statistical equivalence within tolerance).

This is the deeper payoff of treating provenance as conformed dimensions rather than as log files: reproducibility becomes a relational query, not an archaeological expedition.
