Event-driven pipelines: the warehouse as a projection

In an event-driven platform, services do not write to the warehouse. They write to their own databases and publish events. The warehouse becomes a read-side projection of those events — a materialised view, rebuildable from the log. This inverts the traditional ETL model: the source of truth moves from the warehouse to the event stream.

Event sourcing ≡ SCD Type 2 at scale

There is a deep equivalence between event sourcing and SCD Type 2 dimensions. An event-sourced service stores every state change as an immutable event; current state is the fold over those events. An SCD Type 2 dimension stores every attribute change as a new row with effective dates; current state is the row where is_current = true. These are the same idea at different scales.

The practical consequence: the warehouse is not a separate truth. It is a projection of the event streams. You can rebuild any fact table or dimension by replaying the relevant topics from the beginning. You can also build new projections (a new feature store, a new search index) without touching the source services — just subscribe to the topics and project.

The outbox → broker → projection flow
A service writes its business change and an outbox row in one transaction. A poller publishes the outbox row to Kafka. Downstream consumers project the event into the warehouse. The schema registry enforces contract evolution. Replays rebuild the warehouse from the log.

Patterns in use

Six patterns cover the bulk of event-driven concerns. Each pattern is enforced by platform-level tooling, not left to individual service teams.

Outbox
Atomic update of state + event publication

Same DB transaction writes the business change AND an outbox row. A poller reads the outbox and publishes to Kafka. At-least-once; consumers must be idempotent on event_id.

CQRS
Write model ≠ read model

Commands produce events; events are projected into multiple read models (the warehouse, the feature store, the search index). Each read model is independently rebuildable from the event log.

Event sourcing
Need full audit history of state changes

The event log IS the source of truth. Current state is a fold over the events. SCD Type 2 dimensions fall out naturally — every change is an event, every event creates a new dimension version.

Saga
Multi-service business transaction

Choreography: each service emits an event that triggers the next. Orchestration: a central orchestrator emits commands. Compensating events roll back. No 2PC.

Idempotent consumer
At-least-once delivery means duplicates

Every event has a unique event_id. Consumers persist the event_id before processing; on retry, the event is recognised and skipped. The warehouse INSERT becomes an INSERT … ON CONFLICT DO NOTHING.

Schema registry
Event contracts must evolve safely

Avro / Protobuf schemas registered centrally. Producers and consumers checked against the registry at deploy time. Backward-compatible changes only (add optional fields, never remove or rename).

SCD Type 2, the classic way

The ETL job detects an attribute change in the source, opens a new dimension row with a new surrogate key, sets effective_from to now and closes the old row with effective_to = now.

This works, but it makes the warehouse the source of truth for change history. The source system has no idea its data was historical — it just overwrote a row. If you want to re-derive history, you can’t: the source has lost it.

SCD Type 2, the event-sourced way

The service publishes a dimension.change event with the old and new values and the effective timestamp. The warehouse projects the event into a new SCD2 row. The event log retains every change forever.

Now history is in the event log, not the warehouse. Re-derive it any time by replaying the topic. Build a different projection (e.g. Type 6 hybrid) without touching the source. The warehouse is a view; the log is the truth.

What this costs

Event-driven is not free. You pay in operational complexity (a Kafka cluster is a distributed system you must run), in eventual consistency (the warehouse is seconds behind the source, not milliseconds), and in developer cognitive load (thinking in events is harder than thinking in CRUD).

The trade is worth it when (a) multiple consumers need the same data, (b) history matters, and (c) you want to add new projections without changing sources. Scientific platforms hit all three: every measurement has multiple consumers (BI, ML, catalog), history is non-negotiable (provenance), and new analysis pipelines appear constantly. For a small CRUD app, none of this is justified — use a database and a cron job.
